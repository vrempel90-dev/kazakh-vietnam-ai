# Charter Aggregation Engine — проект архитектуры

Дата анализа: 24.09.2026. Статус: **проект решения, без действующих интеграций**. Текущий репозиторий содержит только React/Vite-прототип с демонстрационными предложениями в `src/Prototype.tsx`; серверного API, PostgreSQL, очереди, реальных тарифов, бронирования и отправки заявок сейчас нет. [Отчёт об источниках](source-integration-report.md) определяет условия допуска каждого адаптера.

## 1. Граница продукта и целевой поток

В каталог попадает **авиабилет или доступный блок мест**, а не цена тура с отелем. Если источник выдаёт только пакетный тур, запись отклоняется до получения отдельной цены и наличия авиабилета. Канал публикации может содержать готовую розничную цену; она не становится себестоимостью. Публикация возможна лишь после подтверждения прав на использование данных, типа цены, её валюты, единицы тарифа, состава сборов и способа повторной проверки.

```text
Партнёрский API/разрешённый feed/Sheet/разрешённый веб-источник
  → отдельный SourceAdapter → RawFlightOffer + provenance
  → нормализация и валидация → SourceOffer + снимок/история
  → PricingEngine → FlightOffer + дедупликация → каталог/API Mini App
                                               → outbox → PublisherService → Telegram
Mini App «Оформить» → серверная revalidation у того же источника
  → подтверждение изменившейся цены → Lead → outbox → менеджер
Админ-панель → источники, правила, публикации, заявки, аудит, ошибки
```

Реализация следующего этапа: один серверный API, отдельные воркеры синхронизации/публикации и PostgreSQL. Планировщик ставит по одному заданию на источник; падение одного задания не останавливает другие. Транзакционный outbox связывает изменение предложения/заявки и внешнюю доставку. Секреты хранятся в secret store окружения, права администраторов и менеджеров задаются ролями. Прототип Mini App подключается к API после появления проверенных предложений; демо-данные не смешиваются с боевым каталогом.

## 2. Контракты источника и состояние допуска

```ts
interface FlightSourceAdapter {
  readonly sourceId: string;
  fetchOffers(context: SyncContext): Promise<RawFlightOffer[]>;
  healthCheck(): Promise<SourceHealth>;
  // Только если партнёр поддерживает точечный поиск/проверку:
  revalidate?(sourceOfferId: string, passengers: number): Promise<RawFlightOffer | Unavailable>;
}
```

`RawFlightOffer` хранит исходный идентификатор, исходную запись/хэш, время получения, ссылку, единицу и основание цены, а также версию парсера. `SourceHealth` хранит статус `ACTIVE | DISABLED | ERROR`, время последней успешной синхронизации, последнюю ошибку и число импортированных предложений. Для каждого из 13 партнёров и 2 каналов планируется отдельная реализация и отдельная конфигурация. Общие библиотеки для HTTP, разбора дат и валидации допустимы; общая логика не подменяет контракт конкретного партнёра. Адаптер без доступа возвращает **ошибку конфигурации/доступа**, не пустой «успешный» импорт.

Состояния допуска источника: `DISCOVERY_REQUIRED → ACCESS_REQUESTED → CONTRACT_VERIFIED → SANDBOX_VERIFIED → ACTIVE`; `DISABLED/ERROR` возможны на любом рабочем этапе. Для `ACTIVE` обязательны: письменное разрешение на автоматический доступ и дальнейшую публикацию, выданный метод/доступ, образцы ответа, карта полей, политика частоты, способ точечной revalidation и испытание на реальном ответе. Наличие веб-формы или JSON/XHR-запроса само по себе не даёт права строить интеграцию. Приоритет исследования: официальный API → документированный/разрешённый JSON/XHR → разрешённый feed → Google Sheets → разрешённый HTML → разрешённая browser automation. CAPTCHA/антибот не обходятся.

Публичный Telegram-канал не даёт Bot API исторический доступ к произвольным сообщениям. Подписка на `channel_post` относится к обновлениям, известным боту; для прямого импорта нужен согласованный доступ бота/экспорт или предоставленный владельцем feed. Своя исходящая публикация требует прав бота в своём канале. [Telegram Bot API](https://core.telegram.org/bots/api).

## 3. Нормализованная модель и хранение

`FlightOffer` содержит все поля ТЗ:

| Группа | Поля |
| --- | --- |
| Идентичность | `id`, `sourceId`, `sourceOfferId`, `sourceUrl` |
| Маршрут | `origin`, `destination`, `departureAirport`, `arrivalAirport`, `departureDate`, `returnDate`, `tripType: OW/RT` |
| Рейс | `nightsMin`, `nightsMax`, `airline`, `flightNumber`, `departureTime`, `arrivalTime`, `baggage`, `availableSeats` |
| Цена | `sourceCurrency`, `sourcePrice`, `markupType`, `markupValue`, `salePrice` |
| Состояние | `status: ACTIVE/SOLD_OUT/EXPIRED/PRICE_CHANGED/PENDING_REVIEW`, `lastCheckedAt`, `createdAt`, `updatedAt` |

Дополнительные обязательные внутренние поля: `priceBasis: NET_CONTRACTED | RETAIL_PUBLIC | UNKNOWN`, `priceUnit: PER_PERSON | PER_BOOKING | UNKNOWN`, `fareKind: FLIGHT_ONLY | PACKAGE | UNKNOWN`, `taxesIncluded`, `baggageIncluded`, `sourceTimeZone`, `availabilityKind: EXACT | LIMITED | UNKNOWN`, `rawRecordHash`, `parserVersion`, `lastSuccessfulSyncAt`, `quoteExpiresAt`, `currencyRateId`, `publicationEligible`, `reviewReason`. Суммы хранятся decimal/integer minor units, коды валют ISO 4217, аэропорты IATA, даты и локальные времена с явной временной зоной. `sourcePrice` nullable: для `RETAIL_PUBLIC` он **неизвестен**; отдельное `retailObservedPrice` не считается затратой. Неизвестные цена/валюта/единица/состав/пакетность переводят запись в `PENDING_REVIEW`.

Хранилище: `sources`, `source_credentials_ref`, `sync_runs`, `raw_offer_snapshots`, `source_offers`, `flight_groups`, `flight_group_members`, `flight_offers`, `pricing_rules`, `pricing_rule_audit`, `fx_rates`, `flight_price_history`, `publications`, `leads`, `lead_events`, `manager_destinations`, `outbox_events`, `integration_errors`, `admin_audit`. Ключ идемпотентности `sourceId + sourceOfferId`; если поставщик не выдаёт стабильный ID, адаптер должен подтвердить безопасный составной ключ до допуска. История и снимки append-only. Таблицы с затратами и контактами закрыты от публичной роли. API Mini App отдаёт только публичный DTO: маршрут, даты, рейс, багаж, наличие с отметкой времени, `salePrice`, валюту и CTA; `sourceId`, `sourceOfferId`, `sourcePrice`, наценку и внутренние ошибки не отдаёт.

## 4. PricingEngine

Правила поддерживают `GLOBAL_PERCENTAGE`, `SOURCE_PERCENTAGE`, `ROUTE_PERCENTAGE`, `FIXED_MARKUP` и область применения (`global`, `sourceId`, `origin+destination`). Детерминированный приоритет: **route fixed → route percentage → source fixed → source percentage → global fixed → global percentage**. Применяется ровно одно наиболее конкретное активное правило; фиксированная наценка задаётся в валюте продажи, процент считается от контрактной нетто-цены. Для каждого правила: `id`, область, значение, валюта для fixed, срок действия, автор, версия. Изменение записывается в `AuditLog` со старыми/новыми значениями, актором и временем. Правила версионируются: результат хранит `pricingRuleId`, версию и входные данные.

Расчёт разрешён только для `NET_CONTRACTED + FLIGHT_ONLY + известная единица тарифа + подтверждённая валюта/сборы`. Если источник не в KZT, нужна проверенная котировка FX с источником и временем; устаревший или отсутствующий курс блокирует публикацию. Формула процентного правила: `salePrice = round(sourcePriceKzt × (1 + p/100), roundingMode)`. Для fixed: `round(sourcePriceKzt + fixedKzt, roundingMode)`. `NONE`, `NEAREST_100`, `NEAREST_500`, `NEAREST_1000` округляют до ближайшего шага, половину шага вверх; до этого расчёт ведётся decimal. Пример: 100 000 ₸ × 1,07 = 107 000 ₸. Розничная цена канала (`RETAIL_PUBLIC`) может быть показана только как **уже готовая цена продавца** после подтверждения владельцем/менеджером, без применения наценки; если основание неизвестно, `PENDING_REVIEW`.

## 5. Дедупликация, выбор предложения, история

Сначала строгий ключ по IATA origin/destination, дате вылета и возврата, OW/RT, нормализованной авиакомпании и номеру рейса при наличии. При отсутствии номера совпадение по маршруту/датам является **кандидатом**, который дополнительно сверяется по времени/перевозчику и при неоднозначности отправляется на ручную проверку. Нельзя объединять разные тарифные классы, багажные условия, цену за группу и за человека. `flight_groups` содержит канонический рейс, `flight_group_members` — все исходные предложения и ссылки. Для выдачи выбирается допустимый source offer: подтверждённая доступность, свежесть, полный тариф, затем минимальная продажная цена и заданный приоритет поставщика; выбор и его версия сохраняются. Один канонический рейс публикуется в канал один раз, если явное правило кампании не требует иного.

`Scheduler` берёт интервал из admin settings с fallback на ENV, добавляет jitter, lease и лимиты частоты каждого партнёра. Каждый запуск пишет `SyncRun` и результат `NEW | UNCHANGED | PRICE_CHANGED | SOLD_OUT | RESTORED | EXPIRED`. `PRICE_CHANGED` — событие/метка перехода; текущее предложение вновь становится `ACTIVE` после обработки публикации. Пропажа записи в одном неуспешном запуске **не** означает `SOLD_OUT`: нужен явный сигнал поставщика или успешный полный снимок и настроенный grace period. `EXPIRED` — истёкшее время рейса/TTL после успешных проверок; ошибки доступа отмечают источник `ERROR`, а предложения как устаревающие, но не распроданные. `FlightPriceHistory(offerId, sourcePrice nullable, salePrice nullable, checkedAt, sourceCurrency, priceBasis, pricingRuleVersion, rawHash)` append-only даже при неизменной цене по политике снимков; удаление истории запрещено.

## 6. Публикация и лид

`PublisherService` читает outbox только для `ACTIVE + publicationEligible`, формирует текст из публичного DTO и публикует **только salePrice**; имя B2B-поставщика, затраты и маржа не попадают в шаблон и логи внешнего сообщения. `Publication(telegramChannelId, telegramMessageId, offerId, canonicalGroupId, payloadHash, status, publishedAt)` имеет уникальный ключ для канала/группы. При изменении — обновление только своего ранее отправленного сообщения; при `SOLD_OUT` применяется `EDIT` (пометка «недоступно»), `ARCHIVE` (снять из активной выдачи и, если возможно, редактировать сообщение) или `DELETE` согласно настройке. Удаление зависит от прав и ограничений Telegram; ошибка приводит в retry/dead-letter, а не к потере события. [Методы и права Telegram Bot API](https://core.telegram.org/bots/api).

Поиск Mini App: откуда, куда, дата, OW/RT, число пассажиров, бюджет; фильтры по аэропорту/городу, авиакомпании, цене и ночам. Карточка показывает маршрут, перевозчика, даты, ночи, багаж, наличие, **продажную** цену, «Подробнее» и «Оформить». Дата последней проверки видна пользователю. Перед CTA сервер проверяет подписанные `initData` Telegram, а не доверяет `initDataUnsafe`; [Telegram Mini Apps: validating data](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

`POST /offers/{id}/revalidate` вызывает **тот же подтверждённый источник**, проверяет ID, маршрут, даты, рейс, тариф, места для выбранного числа пассажиров, цену и состав. При `AVAILABLE` сервер выдаёт краткоживущую подписанную quote с `offerId`, `sourceOfferId`, `salePrice`, `passengers`, версией и expiry. При изменении цены/маршрута возвращает новую **продажную** цену и требует явного подтверждения; подтверждение повторно проверяет источник/версию. При `SOLD_OUT` показывает «К сожалению, этот вариант уже недоступен.» и актуальные альтернативы. `UNKNOWN`/timeout блокирует оформление. Источник без точечной revalidation не допускается к автоматическому оформлению; возможна только заявка на ручную проверку с ясной пометкой, без гарантированной цены. Наличие quote не является бронью или гарантией неизменной цены у поставщика.

После успешной revalidation и согласия клиента `POST /leads` по идемпотентному ключу создаёт `Lead(id, offerId, telegramUserId, passengerCount, customerName, customerPhone, salePriceSnapshot, status, assignedManagerId, createdAt)`. Статусы: `NEW → CONTACTED → BOOKING → PAID → CONFIRMED`, либо `CANCELLED`; каждый переход аудируется. Клиент видит «Заявка создана. Менеджер поможет завершить оформление.» и кнопку «Написать менеджеру». Админ задаёт Telegram/WhatsApp destination; доставка через официально доступный метод или открытие `wa.me`/Telegram-чата, если автоматическая отправка не подключена. Сообщение авторизованному менеджеру содержит номер заявки, маршрут/даты/OW-RT, авиакомпанию, багаж, места, продажную цену, пассажиров, контакт и внутренний source offer ID. Себестоимость доступна только staff-роли в админке, не уходит клиенту. Контакты и переписка подчиняются политике хранения/доступа; паспортные данные на этапе лида не собираются.

## 7. Админка, мониторинг, контроль допуска

Разделы: **Источники, Рейсы, Цены, Наценки, Публикации, Заявки, Менеджеры, История цен, Ошибки синхронизации**. «Источники» показывает имя, тип интеграции, `ACTIVE/DISABLED/ERROR`, last successful sync, last error, imported count и manual Sync; ручной запуск проходит через ту же очередь и лимиты. В «Наценках» — preview расчёта и журнал аудита. Права: `ADMIN` управляет источниками/правилами/получателями, `MANAGER` работает с лидами, `VIEWER` видит разрешённые отчёты; затраты доступны только явно уполномоченным сотрудникам.

Логи/метрики: ошибки sync и parse, изменения цен, ошибки публикации/Telegram API, revalidation и доставки лидов; каждая запись содержит `sourceId`, `syncRunId`, `offerId`, correlation ID, тип, время, retry count и безопасное диагностическое сообщение без секретов/PII. Метрики: успешность/длительность по источникам, свежесть каталога, доля `PENDING_REVIEW`, изменения цен, размер outbox/dead-letter, доля failed revalidation. Алерты при длительной потере источника, пустом полном снимке, массовом падении парсинга, росте отказов публикации и задержке менеджерских сообщений. Нет silent failure: любой failed job остаётся видимым и повторяемым.

## 8. План внедрения и критерии приёмки следующего этапа

1. Получить от владельцев партнёров разрешения, доступы, описание тарифа, частоту обновления и точечную проверку. Зафиксировать выбранный метод для каждого источника в [отчёте](source-integration-report.md).
2. Добавить PostgreSQL-миграции, серверный API, роли, secrets и outbox; реализовать доменные контракты, PricingEngine, историю, нормализацию и изолированный Scheduler на синтетических тестовых данных. Демонстрационные предложения не должны попадать в боевую выдачу.
3. Реализовывать **один подтверждённый SourceAdapter за раз**; на реальных разрешённых ответах проверить отображение тарифа, валюты, availability и revalidation. Только затем менять его статус на `ACTIVE`.
4. Подключить каталог Mini App, публикацию в собственный тестовый канал, затем production-канал, и handoff менеджерам. Проверить цену на экране/в Telegram/в заявке, отсутствие внутренних полей в клиентском API и поведение при смене цены/распродаже/ошибке источника.

Перед production-парсерами нужен обзор этого отчёта и партнёрские доступы/разрешения. Сейчас ни один источник не соответствует критерию `ACTIVE`; поэтому живые цены, автопубликация и оформление не должны включаться.
